# 渲染工作台（Render Studio）評估與 V1 交付說明

> 撰寫日期：2026-10-09　對象：Banson、設計主管、後續開發者
> 依據：`協作報告_20261009`（中道森活一樓四輪 + 二樓／三樓／宜蘭游公館三案）、`璞石集團渲染工作台 V2.2` HTML、本次以程式實測的圖面數據。
> 數字標註：【實際】＝報告內已核對或本次實測；【示意】＝假設模型（附條件）。

---

## Key Takeaways

1. **水波紋不是提示詞寫不好，是工作流造成的「世代劣化」。** 每一輪都拿上一輪 AI 輸出當底圖、整張重新生成；輸出還從 2048×1152 掉到 1672×941（像素少 33%）【實際】，再被拿去當下一輪底圖。v3 用了 40 筆生成仍有角落殘紋【實際】——同一方法加碼只會遞減。
   → 工作台改為：**從 3D 原圖單跳**＋**框選區域只改框內**＋**匯回時選區外回貼原像素、放大回原尺寸**。
2. **擺件 A 變 B，是因為每張圖都靠文字重新「想像」物件。** 修法是把物件定成一份規格＋一張從核准主圖裁出的參考圖，並記錄每個視角是否可見；主圖核准後衍生視角才開工，主圖改版自動標記衍生圖「需重驗」。
3. **空間尺度跑掉有量化證據：** 以對位演算法比對原圖，**34 視角 v3/v4 被 AI 放大約 5%、下移約 55 px（2048 寬換算）**；33 視角約 0.6–2.4% 縮放漂移；20、29 幾乎沒有【實際，本次實測】。→ 匯入時自動校正回原鏡位。
4. **360 環景：四個不同位置拍的角度（20/29/33/34）物理上縫不成真實環景**（視差）。正確做法是 3D 軟體在同一點位輸出：直接 360 全景 ＞ 6 面立方體 ＞ 4 張水平 100°。工作台已能縫合、校色、接縫檢查、匯出客戶用單檔 HTML。
5. **V2.2 的治理骨架（設計鎖、參考圖角色、遮罩外合成、付費同意、主管核准）全部值得沿用**；缺的是「專案／多視角」層級、劣化防護與自動檢查——V1 補上這一層。

## 一、本次實測證據

### 1. 水波紋疑似面積（偵測器 vs 3D 原圖）【實際】

偵測方法：帶通濾波抽出 3–12 px 細紋能量，排除物件輪廓，與 3D 原圖同位置比較「多出來的紋理」。

| 視角 | v1 | v2 | v3 | v4 | 解讀 |
|---|---|---|---|---|---|
| 33 客廳正景 | 6.0% | 5.1% | 2.5% | **0.3%** | v3 地毯迷宮紋被精準框出；v4 改素面氈後清掉 |
| 34 客廳望餐廚 | — | — | 2.8% | **0.3%** | v3 右下地毯殘紋 |
| 29 電視牆 | — | — | 0.7% | 0.4% | |
| 20 餐廚 | 1.5% | 1.9% | 2.0% | 1.5% | 主要是百葉門條紋日光影（誤報型態） |

- 趨勢與四輪人工觀察一致，可作為「篩查」工具。
- 已知誤報：百葉／格柵條紋光影、薄紗窗簾褶。所以介面定位為「疑似區＋人工以 100% 原尺寸判定」，不宣稱零瑕疵。

### 2. 鏡位漂移（AI 輸出 vs 3D 原圖）【實際】

| 視角 | 縮放 | 位移（2048 寬換算） | 判讀 |
|---|---|---|---|
| 34 v3／v4 | 約 +5% | 約 26–32, 54–58 px | AI 擅自重新構圖，沙發輪廓也變了 |
| 33 v1–v4 | +0.6～+2.4% | 約 6, 13–19 px | 輕微 |
| 20、29 | ≈0 | ≈0 | 穩定 |

→ 這解釋了「每個空間的尺度大小要一致」為何難：AI 會悄悄縮放構圖。工作台匯入時自動對回原圖；剩下的局部變形（例如沙發形狀）由人工檢查清單把關。

## 二、V2.2 工作台：沿用 vs 優化

| V2.2 功能 | 判斷 | 在 V1 的做法 |
|---|---|---|
| 集團設計鎖（格局／櫃體／設備／擺設／燈具／窗景不可移除） | **沿用** | 變成「保留鎖定」積木（預設勾選）＋畫布「鎖定區」 |
| 模板＝輸入要求＋修改範圍＋參考用途＋驗收規則 | **沿用並拆細** | 拆成可組合的「提示詞積木」（保留／素面材質／光線／一致性／風格／輸出），每塊附中文說明 |
| 局部遮罩＋選區外由原圖合成 | **沿用並升級** | 加上自動對位、羽化；連 ChatGPT 手動模式（不能上傳遮罩）也能在匯回時回貼 |
| 參考圖角色不得互換 | **沿用並擴充** | 角色：已核准主圖／物件／材質／風格／標註示意；Image 1 永遠是底圖 |
| 多視角延伸需「已核准主圖」 | **沿用並自動化** | 衍生視角自動帶入核准主圖、釘選其雜湊；主圖改版 → 衍生版本自動「需重驗」 |
| 付費同意、不自動重試、金鑰只在伺服器 | **沿用** | `/api/render/generate`，預設關閉；逾時記為「結果未知」不盲目重送 |
| 主管核准／退回 | **沿用並分層** | 已生成 ≠ 已檢查 ≠ 已核准；核准必填核准者、時間 |
| 品質檔位（API 計費） | 沿用 | 標準／高品質 |
| 參考圖上限 3 張 | **放寬** | 手動 6 張、API 4 張（主圖＋物件裁切常需要 3 張以上） |
| 角色通行碼 | **取代** | 改用 Email magic link 登入（獨立白名單，與營運儀表板分開） |
| 市場功能追蹤頁 | **不併入** | 屬研發治理，留 V2.2 或改 Notion 週報；不影響設計師日常操作 |
| 「不確定／假設事項」欄位 | **待補（P1）** | 目前以「需求原文」＋物件「提案中／已定案」標示 |
| 單張為中心的介面 | **重做** | 改為「專案畫布」：每個視角一條泳道（原圖 → v1 → v2…），主圖→衍生依賴線 |
| 無劣化防護、無自動檢查、無 360 | **新增** | 世代深度 G0/G1…、水波紋篩查、鏡位校正、物件聖經、一致性對照、360 縫合 |

## 三、四輪＋三案協作流程評估

### 有效、應固化成流程的

| 做法 | 證據 | V1 對應 |
|---|---|---|
| 先做主圖（20 餐廚、33 客廳），再做衍生 | v4 一致性明顯優於 v1–v3 | 主圖／衍生角色、核准閘門 |
| 具體「換材質」比抽象「去紋」有效 | 地毯從羊毛描述 → 素面氈才乾淨 | 素面材質積木（地毯／布面／窗簾／地磚／塗料） |
| 空間方位取代畫面左右 | 29 與 33 茶几左右相反 | 物件「空間錨點」欄位、一致性積木 |
| 原文、提示詞、成品雜湊分開保存 | 報告可追溯 86 筆生成 | 版本保存原文＋編譯提示詞＋SHA-256＋manifest |

### 失效、造成重工的（對應到工具規則）

| 問題 | 發生於 | 後果 | 工具規則 |
|---|---|---|---|
| 同一對話連續修第二、三次 | 一樓 v2→v3 | 全圖重生成、紋理一代代變差 | 每版開新對話（任務包說明寫明）；修正必須框選；世代深度 ≥2 警示 |
| 助理自選款式未標「提案」 | v2 雪花石吊燈 → v3 推翻改藤編 → v4 再換花瓣燈 | 三輪燈具重做 | 物件「提案中／已定案」；定案需主管同意 |
| 「微微亮光」沒有量化 | v2 → v3 使用者說太亮 | 浪費一輪 | 光線積木改成可檢查的描述（白天關閉、無亮點光暈） |
| 「approved」只是助理內部用語 | 四輪歷史 | 誤以為已驗收 | 核准必填核准者＋時間，機器檢查不等於核准 |
| 無上限重跑 | v3 共 40 筆 | 成本與時間失控仍有殘紋 | 修正上限（預設 2 次），達上限提示人工判斷 |
| 錯房、錯端擺件、層架混淆 | 二樓 | 物件位置錯 | 物件標註＋空間錨點；看不到的物件明確「不要加」 |
| 比例分母誤解（1/3 指牆面不是全圖） | 三樓 TV 牆 | 多一輪修正 | 框選區域＋區域指令（座標以框為準） |
| 室內玻璃門被畫成戶外 | 宜蘭 1F | 空間語意錯 | 鎖定區＋保留積木；建議新增「玻璃／鏡面語意」積木（P1） |

## 四、決策題

### 1. 360 環景路線

| 方案 | 空間真實性 | 成本 | 一致性 | 判斷 |
|---|---|---|---|---|
| A. 3D 軟體同點位直出 360 → 工作台切 6 面 → 逐面 AI 優化（同一主圖參考）→ 縫回＋校色 | 高（幾何來自模型） | 設計師多輸出一張全景 | 接縫需檢查（工具已有接縫報告） | **推薦** |
| B. 同點位輸出 4 張水平 100°（或 6 面）→ 直接縫合 | 中高；4 張時天花／地板需補色 | 低 | 同上 | 可用；Enscape／D5 無法直出全景時的備案 |
| C. AI 從單張圖「生成」全景 | 低（看不到的區域全靠想像） | 低 | 差 | **不建議給客戶**，只能當概念氛圍 |

風險：AI 逐面優化會讓接縫附近幾何漂移 → 接縫報告標「檢查」時，以同一主圖參考重修該面邊緣。

### 2. 生成供應商

| 方案 | 成本 | 一致性控制 | 判斷 |
|---|---|---|---|
| ChatGPT 手動（現況）＋工作台任務包／回貼 | API 成本 0；人工上傳下載 | 中（無遮罩，靠回貼補救） | **短期主力** |
| OpenAI API（工作台內建，需管理員開） | 依張計費【示意：需實測單張成本】 | 中高（真遮罩、多參考） | 中期：月量穩定後開 |
| 回 3D 引擎改材質重渲（D5／Enscape） | 設計師工時 | 最高（同一組模型資產） | 長期：關鍵物件與 360 |

## 五、風險（依優先序）

1. **財務**：API 計費。已做伺服器端開關、每次 1 張、不自動重試、結果未知不重送；**尚未做伺服器端月預算上限**（需資料庫，P1）。
2. **法律／保密**：建商樣品屋圖面上傳至 OpenAI／ChatGPT 是否符合與建商的保密條款，需確認合約（需專業人士最終確認）。V1 圖面只存在本機瀏覽器，除非使用者主動匯出或送 API。
3. **單點故障**：V1 資料存在單一瀏覽器 IndexedDB，換電腦即不見 → 必須用「專案備份」；伺服器儲存與多人共用列 P1。
4. **品牌**：AI 優化圖是「示意」不是施工依據；交付 manifest 已寫明「2D 影像編修不能證明毫米級尺寸不變」。建議對外圖面一律標「AI 優化示意」。

## 六、設計師 SOP（V1）

1. 首頁建專案（只填案號），或載入「中道森活一樓」範本。
2. 每個視角拖入 **3D 原圖**（建議 2048 px 以上；原圖唯讀）。
3. 主圖先做：按「新版本」→ 寫需求原文 → 框選要改的區域、每區寫一句要改成什麼 → 勾積木。
4. 「生成」頁下載 **ChatGPT 任務包** → 開新對話、依編號上傳、貼提示詞 → 下載結果。
5. 回工作台「匯入 AI 結果」→ 系統自動放大回原尺寸、校正鏡位、回貼選區外、跑水波紋篩查。
6. 「驗收」頁用 100% 檢視四角與布面，逐項判定 → 送主管核准。
7. 主圖核准後做衍生視角（自動帶入主圖參考）；需要時在主圖用「物件」框選並「存為參考」。
8. 修正一律「開修正版本、框選問題區」，不要在 ChatGPT 同一對話連續要求重修；達修正上限就停下來人工判斷。
9. 全部核准後「交付」頁下載交付包（成品＋原圖對照＋提示詞＋manifest），並匯出專案備份。

## 七、技術說明（給開發者）

| 模組 | 路徑 | 說明 |
|---|---|---|
| 頁面 | `app/(studio)/`、`app/(studio)/p/[projectId]/` | 專案列表、專案工作區（畫布／物件聖經／360／交付） |
| 領域型別 | `lib/render/types.ts` | 視角、版本、區域、場景物件、全景 |
| 提示詞 | `lib/render/prompt-blocks.ts`、`compiler.ts` | 積木庫、編譯器（目標與角色 → 保留 → 本輪修改 → 場景契約 → 材質／光線 → 排除） |
| 狀態機 | `lib/render/workflow.ts` | 已生成／待檢查／待修正／待核准／已核准／需重驗；主圖改版連鎖失效 |
| 影像管線 | `lib/render/composite.ts`、`qa/align.ts` | 回原尺寸、鏡位對位、選區回貼、遮罩、標註示意圖 |
| 水波紋篩查 | `lib/render/qa/ripple.ts` | 純函式，可在 Node 重跑驗證 |
| 360 | `lib/render/pano/` | 縫合（校色、羽化、補色、接縫報告）、WebGL 檢視器、客戶 HTML、全景切 6 面 |
| 儲存 | `lib/render/db.ts` | IndexedDB（V1 本機）；交付／備份 ZIP 由 `zip.ts` 產生 |
| API | `app/api/render/generate`、`status` | 預設關閉；需 `RENDER_LIVE=1`、`OPENAI_API_KEY`、`OPENAI_IMAGE_MODEL`（依當期官方文件填模型 ID）；未以真金鑰實測 |

畫布、ZIP、WebGL 檢視器皆自寫，不依賴第三方繪圖套件。本專案自 2026-10-10 起從營運儀表板（Pure-Dashboard）獨立為 `pure-render-studio`，有自己的登入白名單與部署。
